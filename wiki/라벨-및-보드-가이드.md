## 라벨

### 타입 라벨 (이슈와 PR에 1개씩)

| 라벨       | 설명                                                         | 이런 때 붙여요                     |
| ---------- | ------------------------------------------------------------ | ---------------------------------- |
| `feat`     | 새로운 기능 추가                                             | 로그인 화면 만들기, 검색 기능 추가 |
| `fix`      | 버그 및 오류 수정                                            | 버튼이 안 눌림, 오류 메시지가 뜸   |
| `docs`     | README, `docs/` 등 레포 문서 작성·수정 (Wiki는 PR 없이 수정) | README에 실행 방법 정리            |
| `style`    | 코드 동작과 무관한 서식·포맷 변경                            | 들여쓰기 정리, 포매터 적용         |
| `refactor` | 기능 변화 없는 코드 구조 개선                                | 긴 함수 나누기, 중복 코드 합치기   |
| `chore`    | 빌드, 패키지, 설정 등 기타 작업                              | 패키지 설치, ESLint 설정           |
| `design`   | UI/UX 디자인 관련 작업                                       | 색상·폰트 변경, 화면 배치 수정     |

### 상태 라벨 (필요할 때 추가)

| 라벨       | 설명                                | 이런 때 붙여요                      |
| ---------- | ----------------------------------- | ----------------------------------- |
| `question` | 논의나 확인이 필요한 질문           | "API 응답 형식을 어떻게 할까요?"    |
| `blocked`  | 다른 작업이나 결정 때문에 진행 불가 | 디자인 시안 대기, 다른 PR 병합 대기 |

### 라벨 붙이는 규칙

- 이슈와 PR에는 **PR 제목 타입과 같은 타입 라벨**을 붙여요.
  - 예: PR 제목이 `feat: 로그인 페이지 UI 구현 (#12)`이면 이슈 #12와 PR 모두 `feat`
- 질문만 하는 이슈(PR이 없는 이슈)는 `question` 라벨만 붙여도 돼요.
- `blocked`를 붙일 때는 **무엇 때문에 막혔는지** 이슈 코멘트로 남겨요. 풀리면 라벨을 떼요.

### 헷갈릴 때

| 바뀐 것                             | 라벨       |
| ----------------------------------- | ---------- |
| 새로운 기능이 생김                  | `feat`     |
| 원래 되어야 하는 게 안 돼서 고침    | `fix`      |
| 사용자에게 보이는 화면 모양만 바뀜  | `design`   |
| 코드 모양만 바뀜 (동작·구조 그대로) | `style`    |
| 코드 구조가 바뀜 (동작은 그대로)    | `refactor` |

## Project 보드

- **모든 이슈는 보드에서 관리해요.** 이슈를 만들면 오른쪽 `Projects`에서 보드를 선택해 추가해요.

### Status: 작업이 어디까지 왔나요?

| Status      | 의미                                      | 언제 옮기나요?                           | 누가                  |
| ----------- | ----------------------------------------- | ---------------------------------------- | --------------------- |
| Backlog     | 해야 할 일 목록. 언제 할지는 아직 안 정함 | 이슈를 만들었을 때                       | 이슈 작성자           |
| Todo        | 이번에 하기로 정했고 담당자가 있음        | 담당자(Assignees)가 정해졌을 때          | 담당자                |
| In Progress | 작업 중                                   | 브랜치를 만들고 작업을 시작할 때         | 담당자                |
| Review      | 리뷰 기다리는 중                          | PR을 `Ready for review` 상태로 올렸을 때 | 담당자                |
| Done        | 병합 완료                                 | PR이 병합되어 이슈가 닫혔을 때           | 자동 (안 되면 담당자) |

> Draft PR로 공유 중일 때는 아직 `In Progress`로 둬요.

### Priority: 얼마나 급한가요?

| Priority | 의미 | 판단 기준                                          | 예                                     |
| -------- | ---- | -------------------------------------------------- | -------------------------------------- |
| P0       | 긴급 | 서비스나 데모가 동작하지 않음, 팀 전체 작업이 막힘 | 배포 사이트 접속 안 됨, main 빌드 실패 |
| P1       | 높음 | 핵심 기능이거나 다른 작업이 이걸 기다림            | 로그인 기능, API 연결                  |
| P2       | 보통 | 일반 작업                                          | 마이페이지 화면                        |
| P3       | 낮음 | 없어도 동작에 문제없는 개선                        | 애니메이션 추가, 문구 다듬기           |

- 판단이 어려우면 일단 **P2**로 두고 데일리 스크럼에서 물어봐요.
- **P0**는 바로 팀에 알려요.
